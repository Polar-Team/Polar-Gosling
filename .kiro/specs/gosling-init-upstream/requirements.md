# Requirements Document

## Introduction

This feature enhances the Gosling CLI `gosling init` command with two improvements: (1) automatic Git repository initialization with upstream remote configuration during Nest creation, and (2) updating the default MG/config.fly and UF/config.fly templates to match the current .fly language specification. Currently, `gosling init` only creates the directory structure, config files, README, and .gitignore — the user must manually run `git init` and add remotes. Additionally, the generated templates use outdated syntax that is incompatible with the current .fly parser.

## Glossary

- **Gosling_CLI**: The Go-based command-line tool for managing Nest repositories, built with the Cobra framework.
- **Init_Command**: The `gosling init` subcommand that scaffolds a new Nest repository.
- **Nest**: The single source-of-truth Git repository containing Eggs/, Jobs/, UF/, and MG/ directories with .fly configuration files.
- **Upstream_Remote**: A named Git remote pointing to the remote repository URL that serves as the canonical source for the Nest.
- **Fly_Template**: A default .fly configuration file generated by the Init_Command for UglyFox (UF/config.fly) or MotherGoose (MG/config.fly).
- **UglyFox_Config**: The UF/config.fly file defining runner lifecycle management, pruning policies, and Apex/Nadir pool rules.
- **MotherGoose_Config**: The MG/config.fly file defining MotherGoose infrastructure: cloud provider, API Gateway, serverless containers, message queues, triggers, database, storage, and service accounts.
- **Interactive_Prompt**: A terminal-based user input prompt presented during `gosling init` execution to collect upstream remote configuration.
- **Block_Label**: A required string identifier following a .fly block type keyword (e.g., `uglyfox "my_name" {`), as mandated by the current .fly language specification.

## Requirements

### Requirement 1: Git Repository Initialization

**User Story:** As a developer, I want `gosling init` to initialize a Git repository in the Nest directory, so that I do not have to manually run `git init` after scaffolding.

#### Acceptance Criteria

1. WHEN the Init_Command completes directory and file creation, THE Init_Command SHALL execute `git init` in the target Nest directory to create a new Git repository.
2. WHEN `git init` succeeds, THE Init_Command SHALL print a confirmation message indicating the Git repository was initialized.
3. IF `git init` fails, THEN THE Init_Command SHALL return an error message that includes the underlying Git error and SHALL NOT proceed to upstream remote configuration.

### Requirement 2: Upstream Remote Configuration Prompt

**User Story:** As a developer, I want `gosling init` to interactively ask me for an upstream remote repository URL and branch name, so that my Nest is connected to a remote from the start.

#### Acceptance Criteria

1. WHEN the Git repository is initialized successfully, THE Init_Command SHALL prompt the user for a remote name with a recommended default value of "main".
2. WHEN the Init_Command prompts for a remote name, THE Init_Command SHALL accept the user pressing Enter to use the default value "main".
3. WHEN the user provides or accepts a remote name, THE Init_Command SHALL prompt the user for the remote repository URL.
4. WHEN the user provides a remote repository URL, THE Init_Command SHALL prompt the user for the branch name with a recommended default value of "main".
5. WHEN the user provides or accepts a branch name, THE Init_Command SHALL add the upstream remote using `git remote add <remote_name> <repository_url>`.
6. WHEN the upstream remote is added successfully, THE Init_Command SHALL print a confirmation message showing the configured remote name, URL, and branch.
7. IF the user provides an empty repository URL, THEN THE Init_Command SHALL skip upstream remote configuration and print a message indicating that no remote was configured.
8. IF `git remote add` fails, THEN THE Init_Command SHALL return an error message that includes the underlying Git error.

### Requirement 3: Non-Interactive Upstream Remote Flags

**User Story:** As a developer, I want to provide upstream remote details via command-line flags, so that I can script `gosling init` without interactive prompts.

#### Acceptance Criteria

1. THE Init_Command SHALL accept a `--remote-name` flag of type string with a default value of "main".
2. THE Init_Command SHALL accept a `--remote-url` flag of type string with no default value.
3. THE Init_Command SHALL accept a `--branch` flag of type string with a default value of "main".
4. WHEN `--remote-url` is provided via flag, THE Init_Command SHALL skip all interactive prompts for upstream remote configuration and use the flag values directly.
5. WHEN `--remote-url` is not provided via flag and standard input is a terminal, THE Init_Command SHALL present interactive prompts for upstream remote configuration.
6. WHEN `--remote-url` is not provided via flag and standard input is not a terminal, THE Init_Command SHALL skip upstream remote configuration without error.

### Requirement 4: Update UglyFox Default Template

**User Story:** As a developer, I want the default UF/config.fly template to use the current .fly language syntax, so that the generated file passes `gosling validate` without errors.

#### Acceptance Criteria

1. THE Init_Command SHALL generate a UF/config.fly template where the `uglyfox` block includes a Block_Label (e.g., `uglyfox "default" {`).
2. THE Init_Command SHALL generate a UF/config.fly template where the `uglyfox` block includes a `mothergoose` attribute referencing a MotherGoose instance name.
3. THE Init_Command SHALL generate a UF/config.fly template where the `apex` block includes `cpu_threshold` and `memory_threshold` attributes.
4. THE Init_Command SHALL generate a UF/config.fly template that includes a `policies` block with at least one example `rule` sub-block.
5. THE Init_Command SHALL generate a UF/config.fly template that conforms to the .fly language specification for the `uglyfox` block type.

### Requirement 5: Update MotherGoose Default Template

**User Story:** As a developer, I want the default MG/config.fly template to use the current .fly language syntax, so that the generated file passes `gosling validate` without errors.

#### Acceptance Criteria

1. THE Init_Command SHALL generate a MG/config.fly template where the `mothergoose` block includes a Block_Label (e.g., `mothergoose "default" {`).
2. THE Init_Command SHALL generate a MG/config.fly template that includes a `cloud` block with `provider`, `yc_folder_id`, and `yc_cloud_id` placeholder attributes.
3. THE Init_Command SHALL generate a MG/config.fly template where the `fastapi_app` block includes `image`, `cores`, `execution_timeout`, `concurrency`, and `service_account` attributes.
4. THE Init_Command SHALL generate a MG/config.fly template where the `celery_workers` block includes `cores`, `execution_timeout`, and `concurrency` attributes.
5. THE Init_Command SHALL generate a MG/config.fly template that uses `git_sync_trigger` as the trigger block name instead of `triggers`.
6. THE Init_Command SHALL generate a MG/config.fly template that uses `mothergoose_queues` as the queue block name with `task_queue` and `dlq` sub-blocks instead of `message_queues`.
7. THE Init_Command SHALL generate a MG/config.fly template that uses labeled `service_account "name"` blocks instead of a `service_accounts` wrapper block.
8. THE Init_Command SHALL generate a MG/config.fly template where the `database` block uses `serverless_mode = true` instead of `mode = "serverless"`.
9. THE Init_Command SHALL generate a MG/config.fly template that conforms to the .fly language specification for the `mothergoose` block type.

### Requirement 6: Updated Next Steps Output

**User Story:** As a developer, I want the post-initialization output to reflect the new Git and upstream remote setup, so that I know what was configured and what to do next.

#### Acceptance Criteria

1. WHEN the Init_Command completes with an upstream remote configured, THE Init_Command SHALL include the remote name and URL in the success output.
2. WHEN the Init_Command completes with an upstream remote configured, THE Init_Command SHALL suggest `git push -u <remote_name> <branch_name>` as a next step.
3. WHEN the Init_Command completes without an upstream remote configured, THE Init_Command SHALL suggest manually adding a remote as a next step.

### Requirement 7: Code Location Convention

**User Story:** As a developer, I want all new code to reside in the `dev-new-features` directory, so that the project's branching conventions are followed.

#### Acceptance Criteria

1. THE Init_Command changes SHALL be implemented in `Polar-Gosling/dev-new-features/internal/cli/init.go`.
2. THE Init_Command changes SHALL NOT modify files outside the `dev-new-features` directory tree.
